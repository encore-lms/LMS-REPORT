03

아키텍처

역할별 웹 화면 하나가 4개의 백엔드 서비스와 1개의 분석 엔진을 사용합니다. 데이터베이스는 서비스마다 RDS 인스턴스를 따로 두고, 각 인스턴스 안에서 다시 스키마로 경계를 나눴습니다.

배포 구성 실측

아래는 Terraform 코드와 실제 AWS 리소스를 대조해 그린 현재 개발 환경(dev)의 배포 구성입니다. 서울 리전 단일 VPC 안에서 퍼블릭 서브넷이 요청을 받고, 데이터는 인터넷에서 직접 닿지 않는 프라이빗 서브넷에만 둡니다.

요청을 처리하는 실행 중 구성 데이터 저장소 미기동 · 보조 · 관리형

블록에 마우스를 올리거나 누르면 사양·경로·연결 대상이 여기에 나옵니다.

2026-08-06 Terraform 코드(terraform/)와 AWS 실조회 결과를 대조해 작성했습니다. 블록에 적힌 사양·기동 수는 조회 시점의 실제 값입니다. 문서 기준일(08-05)보다 하루 뒤 시점입니다. 웹 프런트 정적 배포는 이 Terraform 구성에 포함돼 있지 않아 그리지 않았습니다. 블록을 누르면 상세가 고정되고, 위 버튼으로 흐름 단계만 보거나 계층을 껐다 켤 수 있습니다. 그림은 우상단 버튼이나 더블클릭 · Ctrl+휠로 확대하고, 확대 상태에서 드래그로 이동합니다.

왜 이렇게 구성했는가

위 구성은 수강생 265명 · 매니저 25명(계정 약 290개) 규모를 가정하고 잡았습니다. 오프라인 집체 교육이라 부하가 하루 중 특정 시각에 몰리는 대신 절대량 자체는 작습니다. 아래 케이스별 가설은 그 가정에서 나온 추정이며 실측이 아닙니다.

부하 케이스 (가설) 몰리는 지점 현재 구성이 받는 방식
강의 시작 전후 10여 분에 265명이 출결 체크 learning-service 출결은 짧은 읽기·쓰기 트랜잭션이라 512 CPU 태스크 1개로 이 피크(수십 RPS 추정)를 받습니다. 가장 넓은 경로(규칙 120)를 맡는 서비스라 메모리도 2048MiB로 가장 크게 잡았습니다.
일과 시작에 로그인·토큰 갱신이 한꺼번에 몰림 auth-user-service · Redis refresh token을 RDS가 아닌 Redis에 둬 토큰 갱신이 DB를 거치지 않습니다. 290계정 전원이 세션을 유지해도 저장량은 수백 KB 수준(추정)이라 cache.t4g.micro 1노드면 됩니다.
과제 마감 직전 파일 제출이 몰림 learning-service · S3 파일 본문은 S3로 가고 서비스는 메타데이터만 다룹니다. 대용량 제출이 태스크 메모리를 밀어내지 않습니다.
매니저 25명이 운영 대시보드·CSV 인입을 동시 사용 operations-service 운영 경로(규칙 90)를 learning의 광역 /admin/*보다 먼저 매칭시켜 수강생 트래픽과 분리했습니다. 동시 사용자 상한이 25명이라 512 CPU/1024MiB로 충분합니다.
증명서 공개 링크로 외부 검증자가 유입 learning-service /verify/* 비로그인 조회 1건 = 읽기 1회입니다. 캐시 없이도 가볍고, 유입이 커지면 CloudFront 캐시를 켜는 선택지가 남아 있습니다.
배포·장애로 태스크가 재시작 전 서비스 태스크가 1개뿐이라 콜드스타트(약 60초) 동안 해당 서비스가 비지만, 이 규모에선 감수합니다. 헬스체크 유예 120초로 재시작이 크래시루프가 되는 것만 막았습니다.

같은 가정에서 일부러 뺀 것도 있습니다. 이 규모가 정당화하지 못하는 비용입니다.

선택 아낀 것 감수한 것
NAT Gateway 없이 ECS를 퍼블릭 서브넷에 배치 NAT 고정비(시간당 + 처리량 과금) 태스크가 공인 IP를 가짐 — 보안그룹으로 ALB에서 오는 인바운드만 허용해 보완
전 구간 단일 인스턴스 — RDS 단일 AZ · Redis 1노드 · 서비스당 태스크 1개 · 오토스케일 없음 대기(standby) 인스턴스 비용 — multi-AZ는 인스턴스 비용이 2배 AZ 장애·재시작 시 수 분 중단. 290명 규모의 교육 서비스라 감수
도메인·인증서 없이 CloudFront 기본 도메인 도메인·인증서 관리 주소가 *.cloudfront.net — HTTPS 자체는 확보
DB는 서비스별 4대로 나누되 전부 db.t4g.micro — 데이터 경계만은 규모와 무관하게 처음부터 나눴습니다. 운영 중에 쪼개는 비용이 훨씬 크고, micro 4대 비용은 큰 인스턴스 1대와 비슷합니다(추정)

이 구성의 한계선과 확장 기준 (추정)

위 케이스들을 종합하면, 가장 붐비는 learning-service 기준으로도 피크 부하는 태스크 1개 처리 용량의 절반에 못 미친다고 추정합니다. 즉 서비스당 태스크 1개인 현재 구성으로 동시 사용자 약 600~800명 — 지금 가정(290명)에서 300~500명을 더 — 수용할 수 있을 것으로 봅니다.

확장 기준은 미리 정해 두었습니다. 클러스터에 켜 둔 Container Insights 지표에서 어느 서비스든 CPU 또는 메모리 사용률이 75%를 넘는 구간이 지속되면, 그 시점에 오토스케일 적용(V2)을 진행할 예정입니다. 그 다음 단계는 순서대로 RDS multi-AZ·읽기 분리 → NAT + 프라이빗 서브넷 이전입니다.

증명서 발급 흐름 결정

제품의 핵심 가치이자 현재 유일하게 끊긴 구간입니다. 수강생이 요청하면 시스템이 학습·프로젝트·평가 데이터를 모아 점수를 내고, 운영자가 검토·승인하면 그 시점의 내용을 그대로 동결합니다. 이후 원본 데이터가 바뀌어도 발급된 증명서는 변하지 않으며, 외부인은 공개 링크로 진위를 확인합니다.

결정 요청 사항

아래 네 가지는 실무에서 결정할 수 없고, 결정이 늦어질수록 8월 종료 가능성이 낮아집니다.

01

8월 종료 범위를 “증명서 축 완성”으로 확정할 것인가

P0만 수행하면 18영업일 안에 들어갑니다. PLAY·데이터연동·UI 통일까지 넣으면 넘칩니다. 증명서는 이 제품의 존재 이유이므로 다른 것을 미루는 편이 합리적입니다.

권고 — P0 4건만 8월 범위로 확정, P2 3건은 9월 이월

02

신규 기능 동결일을 언제로 할 것인가

현재 신규 요청이 계속 유입되어 QA 기간을 잠식하고 있습니다. 동결일 이후 요청은 릴리즈 차단 결함이 아닌 한 자동으로 9월 백로그로 넘깁니다.

권고 — 2026-08-07(금) 동결, 이후 결함 수정만

03

증명서를 실데이터로 종료할 것인가, 합성 데이터 시연으로 종료할 것인가

현재 분석 엔진은 합성 수강생 300명 데이터로 계산합니다. 실데이터 전환은 2~3일이 들고, 전환 후 점수·등급이 달라져 재검증이 필요합니다. 합성 데이터로 종료하면 일정은 안전하지만 “실제로 쓸 수 있는가”에 답하지 못합니다.

권고 — 실데이터 전환. 단 3주차에 재검증 시간을 명시적으로 확보

04

자동 회귀 시험을 8월 안에 구축할 것인가

원 QA 계획에는 있으나 미착수입니다. 지금 전면 구축하면 증명서 구현 시간을 잠식합니다. 구축하지 않으면 릴리즈 직전 회귀를 사람이 손으로 확인해야 합니다.

권고 — 핵심 5개 시나리오만 자동화, 나머지는 수동 체크리스트로 대체

한 줄 요약

제품의 87%는 이미 실제로 동작합니다. 남은 13%가 하필 제품의 이름값인 ‘증명서’에 몰려 있습니다. 8월 종료 가능 여부는 기술 난도가 아니라 “지금부터 증명서만 할 것인가”라는 범위 결정에 달려 있습니다.

본 보고서의 실측 표시 수치는 2026-08-05에 저장소 코드와 배포 환경(웹·API)에서 직접 측정했습니다. 화면 수는 라우트(주소) 단위 기준이며, 설계 문서의 Figma 프레임 단위 집계(활성 255장)와는 세는 방식이 다릅니다. 일정의 소요일 추정은 지난 4주 실적 속도를 근거로 한 추정치이며 확정값이 아닙니다.
