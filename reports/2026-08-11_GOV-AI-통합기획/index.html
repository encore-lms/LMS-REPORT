GOV-AI × LMS
통합 기획안

정부지원 AI 활용 교육 사업(GOV-AI-Agent)과 LMS 역량증명서를 어떻게 하나로 잇는지에 대한 우리 측 안입니다.

두 시스템은 겹치지 않습니다. GOV-AI는 학습 과정에서 나오는 원천 데이터를 만들고, LMS는 그것을 평가·인증·증명으로 바꿉니다.
따라서 통합의 실체는 시스템 합병이 아니라 데이터 계약 한 건입니다.

이 문서는 그 계약에 무엇이 들어가야 하는지, 그래서 외부 개발 주체에 무엇을 요청해야 하는지를 정리합니다.

01

요약

GOV-AI-Agent는 제안서와 3명 규모의 개념검증(PoV)까지 나와 있습니다. 수집 파이프라인·분석 엔진·대시보드의 실물은 아직 확인되지 않습니다. 제안서 로드맵대로면 9월 중순은 2단계(LLM 분석·리포팅) 진행 중이므로, 그 시점에 완성된 시스템을 전제로 계획을 세울 수 없습니다.

두 시스템의 역할은 겹치지 않습니다. GOV-AI는 학습 과정(코딩 시도·에러·질문)을 남기고, LMS는 그것을 평가·인증·증명서로 바꿉니다. 우리 역량증명서 6축 중 기술·문제해결·학습지속성 3축이 지금 데이터 부족으로 얕은데, GOV-AI 이벤트가 정확히 그 자리를 채웁니다.

그래서 통합의 실체는 시스템 합병이 아니라 데이터 계약 한 건입니다. 계약이 서면 나머지는 각자 개발입니다. 계약을 정의해서 건네는 쪽이 우리여야 하며, 그 초안이 이 문서의 4장 요구사항 명세서입니다.

가장 먼저 풀어야 할 충돌 — 가명화 vs 실명 증명서

GOV-AI 제안서는 수집 시점의 식별정보 분리·가명화를 개인정보 보호 방침으로 명시합니다. 그러나 우리 역량증명서는 개인 실명으로 발급되어 외부 검증까지 되는 문서입니다. 가명화된 학습 데이터를 증명서 근거로 쓰려면 재식별 키와 그에 대한 동의 범위가 필요합니다.

이것은 개발 순서 문제가 아니라 설계 전제 문제라, 화요일 회의에서 먼저 정리되지 않으면 이후 모든 스펙이 다시 흔들립니다.

연결하는 쪽으로 간다면 방법은 이미 있습니다 — 실습 환경 진입 시 이미 배포된 LMS 로그인 API로 인증하게 하면 그 시점부터 모든 데이터가 수강생별로 쌓입니다 (4장 R1-A).

02

GOV-AI-Agent × LMS 통합 서비스 기획안

기준은 하나입니다. 우리 LMS에 이미 있는 자산과 GOV-AI 데이터가 만나야 성립하는 기능만 넣었습니다. 둘 중 하나만으로 되는 것은 통합 안건이 아니라 각자의 개발 항목입니다.

F1. 나의 역량 히스토리 1차

수강생이 실습 환경과 LMS에서 수행한 학습·실습·프로젝트 데이터를 일자별로 모으고 기술 카테고리별로 분류해, 학습 과정과 역량 성장 과정을 시각화합니다. 지금의 증명서가 “수료 시점의 한 장”이라면, 이것은 “거기까지 온 경로”입니다.

구분 내용
화면 위치 별도 페이지를 만들지 않고 수강 역량 증명서 안의 탭으로 넣습니다. 독립 역량 리포트 페이지는 이미 증명서로 통합하기로 결정된 바 있어, 되돌리지 않습니다
우리가 이미 가진 것 과제 제출, 퀴즈 응시·결과, 프로젝트 활동, 트러블슈팅, 출결, 학습 기록(블로그·스터디·자격증) — 모두 날짜를 가진 채 DB에 있습니다. 시간축으로 세우는 것 자체는 우리 쪽 작업입니다
GOV-AI에서 받아야 할 것 일자별 실습 이벤트(ts · type · step) — 시험과 시험 사이의 빈 구간을 채우는 유일한 소스
지금 없는 것 기술 카테고리 분류 체계가 양쪽 모두 없습니다. GOV-AI 이벤트에는 step(1~10) 숫자만 있고 그 단계가 어떤 기술인지 정의가 없으며, 우리 과제·퀴즈에도 동일한 분류 축이 없습니다. 이것 없이는 “카테고리별”이 성립하지 않습니다
9월 중순 시연 부분 가능 실 연동 대신 배치로 받은 이벤트 파일로 화면을 채우는 수준

기술 카테고리 사전은 우리가 정의해서 건네는 것이 맞습니다

이 분류는 증명서에 표시되는 항목이고, 우리 과제·퀴즈·프로젝트도 같은 축으로 묶여야 합니다. 상대가 정의한 분류를 나중에 받아 맞추면 우리 데이터 전체를 다시 태깅해야 합니다. 우리가 카테고리 사전을 만들어 제공하고, GOV-AI는 이벤트에 그 값을 태깅해 돌려주는 방향을 제안합니다.

F2. 수준별 맞춤 AI 티칭 2차

수집된 실습 데이터를 근거로 수강생별·기술 카테고리별 난이도를 AI가 산정하고, 그 난이도에 맞는 문제를 자동으로 출제합니다.

구분 내용
우리가 이미 가진 것 퀴즈 출제·템플릿·문항 관리와 자동 채점이 이미 구현·배포되어 있습니다. 출제 엔진을 새로 만들 필요가 없습니다
GOV-AI에서 받아야 할 것 카테고리별 수준 판정 — 학생 × 카테고리 단위의 난이도 값과 그 근거
지금 없는 것 현재 진단은 학생당 등급 하나(초급·중급·해결사)입니다. “Python은 중급이지만 자료구조는 초급” 같은 카테고리별 분해가 없어, 지금 값으로는 카테고리별 출제를 할 수 없습니다. 우리 문항에도 난이도·카테고리 태그가 없어 양쪽 모두 확장이 필요합니다
9월 중순 시연 불가 F1의 카테고리 체계가 선행되어야 성립. 10월 이후 범위로 봅니다

이 기능의 역할 분담은 명확합니다. 판정은 GOV-AI, 출제와 채점은 우리입니다. 상대가 출제까지 만들면 우리 퀴즈 시스템과 이중 관리가 되고, 수강생은 문제를 두 군데서 풀게 됩니다.

04

요구사항 명세서

회의에서 “무엇을 만들어 주세요”라고 말하면 상대가 만든 결과를 우리가 받아 맞추게 됩니다. 그 순서가 뒤집히지 않도록, 주고받을 데이터의 모양을 우리가 먼저 정의해 문서로 건네는 방식을 제안합니다.

요청의 3원칙

01

시스템 통합이 아니라 데이터 계약이다

서로의 시스템을 열어 주는 것이 아니라, 주고받을 데이터의 형식·주기·경로만 합의합니다. 계약이 서면 그 뒤로는 각자 개발입니다. 상대 시스템의 내부 구현은 우리 관심사가 아니고, 그 반대도 같습니다.

02

식별자와 분류 체계는 우리가 정의해 제공한다

데이터의 최종 소비처가 실명으로 발급되는 역량증명서이기 때문입니다. 학생 식별자와 기술 카테고리 사전을 우리가 만들어 건네고, 상대는 그 값을 붙여 돌려줍니다. 반대로 하면 우리 기존 데이터 전체를 다시 태깅해야 합니다.

03

점수 산정은 LMS-AI 한 곳에서만 한다

GOV-AI는 원천 데이터와 판정 근거까지 제공하고, 증명서 점수는 우리 엔진이 확정 함수로 계산합니다. 승인된 증명서는 재실행해도 같은 값이 나와야 하므로, 점수를 두 곳에서 만들 수 없습니다.

R1-A. 학생 특정 방법 — LMS 로그인 API 연동 실측

매핑 테이블을 따로 만들어 주고받는 방식은 계정이 추가·변경될 때마다 어긋납니다. 실습 환경에 진입할 때 수강생이 LMS 계정으로 한 번 로그인하면, 그 시점부터 모든 이벤트가 우리 수강생 식별자에 자동으로 묶입니다. 별도 동기화가 필요 없고, 재직·수료 상태도 LMS 기준으로 항상 맞습니다.

아래는 이미 배포되어 동작 중인 API입니다. 신규 개발 없이 바로 붙일 수 있습니다. 응답은 모두 { data: … } 로 감싸여 있습니다.

엔드포인트 요청 응답

붙일 때 확인해야 할 두 가지

① refresh token 이 HttpOnly 쿠키입니다. 브라우저를 전제로 만든 방식이라, VSCode 확장이나 터미널 앱처럼 브라우저가 아닌 클라이언트에서는 쿠키를 직접 보관·재전송하는 처리가 필요합니다. 그것이 어려우면 비브라우저 클라이언트용 토큰 발급 방식을 우리 쪽에서 추가하는 것으로 협의합니다.

② 식별자는 user.id 하나로 고정합니다. studentUuid 는 이름과 달리 로그인 ID이고 수강생 역할에서만 채워집니다. 두 값을 섞어 쓰면 나중에 어느 쪽 기준으로 쌓인 데이터인지 구분할 수 없게 됩니다.

아래 세 가지는 정해지지 않으면 명세가 확정되지 않는 항목입니다.

D1

학습 데이터를 가명화 상태로 둘 것인가, 증명서에 연결할 것인가

GOV-AI 제안서는 수집 시점 가명화를 방침으로 두고, 우리 역량증명서는 실명으로 발급되어 외부 검증까지 됩니다. 가명화를 유지하면 실습 데이터는 그룹 통계로만 쓸 수 있고 개인 증명서 근거로는 못 씁니다. 연결하려면 재식별 키와 동의 문안 수정이 함께 필요합니다.

권고 — 연결하는 방향. 실습 환경에 LMS 로그인을 붙이는 R1-A 방식이 가장 단순하고, 우리 쪽 신규 개발도 필요 없습니다. 다만 동의 문안 수정이 선행 조건임을 회의에서 명시

D2

기술 카테고리 사전을 우리가 정의해 제공하는 것에 합의할 것인가

“카테고리별 역량 히스토리”와 “카테고리별 맞춤 출제”가 모두 이 사전 위에 섭니다. 상대가 먼저 정의하면 우리 과제·퀴즈·프로젝트 데이터를 전부 다시 태깅해야 합니다.

권고 — 우리가 초안을 만들어 배포. 회의에서 승인만 받는 형태

D3

1차 연동을 파일 배치로 시작할 것인가

상대의 Collector API는 2단계 범위이고 현재 확인되는 산출물은 파일뿐입니다. API를 기다리면 9월 중순에 보여줄 것이 없고, 파일 배치로 시작하면 계약(스키마)만 맞으면 나중에 API로 갈아끼울 수 있습니다.

권고 — 1차 파일 배치, 2차 API 전환. 스키마는 처음부터 API 전제로 설계

이 명세의 성격

API 스펙과 현행 데이터 구조는 저장소에서 확인한 사실이고, 요청 항목과 계약 초안은 우리 측 제안입니다. 확정된 합의가 아니며, 회의 결과에 따라 바뀌는 것을 전제로 작성했습니다. 회의 후에는 합의된 값을 이 문서에 반영해 같은 날 회람합니다.

인력 부하

현재 개발 인력은 3명이고, 8월 31일 증명서 마감이 그대로 살아 있습니다. 08-07 회의에서 이미 평일 야간과 주말까지 이어지는 작업 부하가 보고됐습니다.

위 일정은 8월 후반 2주에 마감과 통합 설계가 겹치는 것을 전제합니다. 그대로 가려면 통합 쪽 설계를 담당 1인으로 한정하거나, 9월 중순 시연 범위를 위 표보다 더 줄이는 선택이 필요합니다. 아래 D5 가 그 판단입니다.

D4

9월 중순 시연 범위를 위 제안대로 확정할 것인가

포함 2건(역량 히스토리 화면 · 배치 적재 1경로), 제외 2건(맞춤 티칭 · 실시간 API)입니다. 9월 중순은 조정 불가한 유일한 고정 일정이므로, 범위를 먼저 좁히지 않으면 셋 다 미완으로 갑니다.

권고 — 제안대로 확정. 인력 판단(D5)에서 더 줄여야 한다면 배치 적재를 수동 1회 반입으로 대체

D5

8월 31일 증명서 마감과 통합 설계를 어떻게 병행할 것인가

8월 후반 2주에 두 작업이 겹칩니다. 현재 인력은 3명이고 이미 야간·주말 작업이 보고된 상태입니다. 선택지는 셋입니다 — ① 통합 설계를 1인 전담으로 분리, ② 9월 중순 시연 범위를 더 축소, ③ 증명서 마감을 조정.
